# PILOT · подготовленный реальный пакет FORMA: корректность хронологии прогресса

**Статус: инженерный кандидат / DRAFT, не включать в защищённый main до совместимости с доверенным публикатором PR #29.**

## Цель и ограничение

ID: `forma-progress-chronology-v1`. Имя очереди: `progress-chronology`. На текущем защищённом base SHA `65a2d8e9a0858267dfb5317d8f89c0e56ba5e35d` функция `countCompletedPlannedDays` засчитывает завершённую тренировку с ошибочной старой хронологией (`finishedMs < startedMs`). Это возможно в повреждённой/устаревшей истории после отката системных часов. Исправление только **фильтрует** запись из показателя прогресса текущего плана; история, сами записи, резервные копии и даты не переписываются.

Модель вправе вернуть **ровно одно Kotlin Boolean-выражение**. Единственные доступные свойства — `it.finishedMs`, `it.startedMs`, разрешены только строго ограниченные идентификаторы и операторы. Единственная изменяемая строка — фильтр `Phase.DONE` в одном файле `domain/src/main/kotlin/ru/forma/domain/WeeklyPlanProgress.kt`. Референс `PROGRESS_FILTER` обязан встречаться на точном SHA **один раз**. Изменённый base или уже применённый фикс не допускают повторной генерации.

Проверка `scripts/ai-pilot/ProgressChronologyTest.kt`: до исправления тренировка, окончившаяся **раньше** начала, не должна засчитываться; равные timestamps и нормальная тренировка должны засчитываться; валидная тренировка сохраняет прогресс несмотря на другую повреждённую запись. Прогон `verify-domain.sh` с зафиксированными Kotlin 2.0.21/JUnit jars проверяет патч до read-only независимого Qwen reviewer. Патч затем проверяется по SHA256 и разрешённому пути, как остальные real tasks.

`scheduled_select.py` сначала проверяет две старые задачи (PR #21, #15); если они заняты, выбирает `progress-chronology` **только при наличии исходного точного маркера** и отсутствии чужого PR на ветке `pilot/task-forma-progress-chronology-v1`. Иначе безопасно переключается на `smoke`. Очередь, CLI, план, JSON integrity receipt, неизменяемая политика single-file patch и синтетический Git-CAS ledger зарегистрируют тот же ID. Отдельная запись только у trusted publisher, никогда у Qwen job.

### Блокер до merge

**PR #29** содержит отдельную таблицу доверенного публикатора `trusted_artifacts.TASKS`, требуемый allowlist `apply_as_data` и `verify_dispatch`. Их необходимо расширить на ID `forma-progress-chronology-v1` и путь `WeeklyPlanProgress.kt` **его единственным writer** после проверки точной базы. Иначе новый artifact может пройти read-only schedule, но доверенный публикатор вернёт FAIL или не признает пакет. Такой producer/consumer mismatch **не активируем** в `main`.

Сначала довести #29 до безопасного merge, затем обновить согласованный trust catalog на отдельной ветке и только после полного CI разрешить настоящий scheduled selection. Любые созданные моделью продуктовые PR остаются Draft до подтверждения Android/backend обязательной регрессии и последующей приёмки владельцем. `repository_dispatch` проверки на default main **не являются** нативными required contexts на product PR HEAD.
