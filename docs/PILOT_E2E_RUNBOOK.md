## Какой именно прогон проверен

`scripts/pilot_task_state.py` — **локальный симулятор доверенного исполнителя**, не вызывающий GitHub API. Для тестов используется только `pilot-synthetic-e2e-v1`, файл `fixture.py`, маленький обратимый diff и `git apply --check` на **чистом отдельном checkout**. Два исполнителя не могут одновременно записывать состояние: `git update-ref` с expected-old SHA — атомарный CAS, а 15-минутный lease препятствует перехвату активной попытки. Патч сохраняется **в Git blob отдельного bare-хранилища вместе с JSON**, так что истечение 7-дневного артефакта Actions не стирает его при наличии долговременного хранилища.

Поля состояния: `task_id`, `package`, `base_sha`, `branch`, `status`, `attempt`, `writer`, `lease_until`, `patch_sha256`, `checks`, `pr_url`, `pr_head_sha`. После прерывания новый исполнитель читает то же `patch.diff`, увеличивает номер попытки, перепроверяет SHA, путь и применимость к точному source base. Изменённая база возвращает `STALE_BASE_REQUIRES_REVALIDATION` и требует нового исследования, а не применения старого патча.

Симуляция завершается `status=PUBLISHED`, `pr_url=simulation://draft/...`, `pr_head_sha=null`; повтор на том же task ID возвращает **тот же** Git-коммит состояния и URL — второго PR нет. Эти значения **не являются настоящей GitHub PR-ссылкой**, а заявка от модели не подтверждает исходное событие/run/тесты. Публикатор с будущими write-привилегиями обязан **самостоятельно** проверить `pilot_safe_output.py` receipt, реальный run ID, исходный SHA, artifact hash, результат другой модели и ревью/компилятор, занятость задачи и применимость patch на актуальном main. Проверять `git apply --check` *и* подписанные GitHub обязательные статусы PR нужно по отдельности.

## Команды запуска

**GitHub Actions — одна команда для существующей read-only очереди** (не требует отдельного платного API; для ручного workflow_dispatch у инициирующей учётной записи должно быть право запуска Actions):

```bash
gh workflow run ai-work-queue.yml --repo spenskoj90-sudo/forma-fitness-android --ref main -f package=smoke -f expected_sha="$(git rev-parse HEAD)" -f batch=all
```

Слово `smoke` выбрано сознательно при уже занятых двух одобренных реальных пакетах. **Ручной dispatch НЕ равен событию schedule**, нельзя записывать его как результат расписания. При независимом одобрении и освобождении конкретного пакета вместо smoke можно выбрать его имя и последнюю точную базу. GitHub cron действует лишь на default branch и без SLA регулярности.

**Linux: один проверяемый автономный синтетический прогон, полностью offline (требует Python 3.11+, Git):**

```bash
python3 scripts/pilot_demo.py
```

**Linux: реальная локальная модельная очередь** (нужны заранее загруженные, проверенные SHA256 веса Qwen/llama.cpp и Kotlin Maven-зависимости; при холодном кэше нужен Интернет):

```bash
bash scripts/ai-pilot/run-queue.sh "$(git rev-parse HEAD)" /persist/forma-pilot/queue smoke
```

Для продукта подставляется имя *свободного одобренного* пакета, и результат остаётся недоверенным до отдельного review/publisher. Каталог `/persist/forma-pilot/queue` должен лежать на реальном постоянном томе; ephemeral GitHub Actions `RUNNER_TEMP` и artifact-only не обеспечивают долговечности.

## При потере GitHub и границы полномочий

Работают без GitHub при наличии кэшированных бинарников/зависимостей: Qwen через loopback llama.cpp, детерминированные тесты, локальный Kotlin и проверка `git apply --check`, чтение и атомарное сохранение Git-CAS ledger на независимом диске, повторная симуляция. Ждут восстановления GitHub: свежий список PR и точный `main` SHA, истинная резервация на удалённом репозитории, запуск/логи GitHub Actions, защищённые обязательные проверки и создание настоящего draft PR. Отдельная независимая машина/сервер вне GitHub **не подключены и не доказаны**; GitHub-hosted Linux CI — независимый job внутри GitHub, а не полноценный автономный хост.

**Необходимое отдельное согласование для живого публикатора:** изолированный job/бот с `contents:write` для одной разрешённой ветки/checkpoint и `pull-requests:write` только для открытия **draft** PR, по возможности отдельный ограниченный GitHub App/token. Структура branch protection и обычные пять проверок сохраняются. Не предоставлять этот токен модельному job. Отдельный `actions:write` понадобится лишь если публикатор будет самостоятельно запускать `workflow_dispatch`; для публикации draft PR он не нужен. `issues:write`, подпись, GitHub environments, production, ключи, B2 и платные облачные API не требуются для этого блока.

Принципиальная граница: синтетический CI PASS ≠ реальное расписание ≠ реальный Qwen-патч FORMA ≠ GitHub draft PR ≠ постоянный подписанный APK или приёмка Infinix/Poco.
